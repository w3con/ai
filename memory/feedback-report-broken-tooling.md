---
name: feedback-report-broken-tooling
description: A script, hook, skill, command, agent or connected server that fails or is missing is reported in the same answer, in one line, even when a fallback got the result anyway
metadata:
  type: feedback
---

When a tool of your own misbehaves — a script that is missing or fails, a hook that does not fire, a skill or slash command that points at something no longer there, an agent that errors, a connected server whose tools are absent — say so in the same answer, in one plain line, naming the thing and what it did. Say it even when a fallback route produced the result. Do not switch quietly to another route and present the answer as though nothing happened.

The line to hold is not "did I get an answer" but "will this happen again on its own". A live provider that returned nothing for this particular query, or a network blip the script retried past, is ordinary and needs no report. A tool that is absent or wrongly configured will fail identically on every future call, forever, until somebody is told — that is the case that must always be reported. Where the repair is cheap and reversible, make it and report what you did rather than asking; see [[feedback-install-what-you-need]] and [[feedback-resolve-before-reporting]].

**Why:** Alex asked on 2026-08-25 why he learns from himself, and not from me, that `/web-search` is broken: «почему ты, когда видишь, что не работает, начинаешь использовать другие инструменты поиска, вместо того, чтобы сообщить, что поиск сломан?» The Validité repository carried its own stale copy of the `web-search` skill, untouched since 14 May, whose first two steps called `mcp__brave-search__brave_web_search` and `mcp__duckduckgo__duckduckgo_web_search` — two servers that had long since stopped being configured anywhere. Because the skill's own text described a fallback ladder, each failure read to me as a normal branch rather than a defect, so the skill fell through to the expensive built-in `WebSearch` every single time and still returned results. From outside it looked like a working search. It cost more, searched worse, and stayed broken for three months, because the only person who could fix it was never told.

**How to apply:** two failure shapes, two behaviours. A fallback that fires because a live thing had nothing to say — stay silent, that is the ladder doing its job. A fallback that fires because a thing is absent, unconfigured or broken — one line in the answer, always. When you write a skill or an agent file that contains a fallback ladder, write that distinction into the file itself, so it does not depend on your own good faith in the moment. This is the same instinct as [[feedback-never-report-your-own-problems]] pointed the other way: that one says do not hand Alex an obstacle you could clear yourself, this one says never hide one you have merely walked around.
