---
name: feedback-spawn-subagents-visibly
description: A task-executor subagent must run in the foreground where Alex can watch it — never hidden inside a wrapper script, never started as a detached/background run. Read-only agents (critics, checkers) are not covered.
metadata:
  type: feedback
---

A subagent that **builds or changes something** — writes code, edits files, commits — always runs in the foreground. Before it runs, say plainly which agent is being raised and what it is being asked to do; then raise it with the visible `Agent` tool call in the conversation and stay with it. Never spawn it inside a wrapper command that hides its turns, and never hand it off as a detached background run whose progress Alex cannot watch as it happens — not `Workflow` (which always runs in the background), not `Agent` with an `isolation`/background mode, not a shell command backgrounded with `run_in_background` when the thing running inside it is itself an executor agent.

**Scope, corrected 2026-08-18.** The rule was first written as covering every subagent without exception, and on that reading `bin/card-launch`'s internal critic reading counted as a violation. Alex corrected this the same day: the rule is about **executors** — the agents that actually do the work and cost real, hard-to-reverse tokens and file changes — not about read-only agents such as `card-critic` or `trace-audit`, which write nothing and only produce findings for review. A wrapper that runs a read-only critic step internally, then stops and hands the coordinator an executor brief to spawn visibly, is not a violation of this rule.

**Why:** Alex said the original, broader version on 2026-08-17, then again the same day in far angrier terms — «ВСЕ СУБАГЕНТЫ ВСЕГДА ДОЛЖНЫ БЫТЬ FOREGROUND» — because the first, softer wording had not stopped it from happening again. An agent he cannot see is an agent he cannot stop, cannot pace, and cannot judge while it is still cheap to change course; by the time a background run or a wrapper prints its result the money is already spent. That concern is real for an executor — it writes code and commits — but does not apply the same way to a read-only critic pass, which is cheap, reversible (it edits nothing), and already gated separately by [[feedback_reviewer_agent]].

**How to apply:** name the executor agent and its task in the message before the spawn, spawn it through the visible `Agent` tool, and do not reach for `Workflow`, an `isolation`/background `Agent` mode, or a backgrounded shell wrapper as a way to run an executor out of sight — even when those tools are otherwise permitted for other reasons (e.g. `Workflow` needs its own separate user opt-in per its own tool description; this rule constrains what happens *if* that opt-in is ever given too — keep the executor step visible turn by turn, don't just wait for the final result). In this project, `bin/card-launch` may be run to completion for its critic-reading, signing and worktree-cutting steps (all read-only or mechanical, no executor involved) — but never with `--start-executor`, since that flag starts the executor itself in a detached background process. Call it without that flag, let it print the executor's brief and prompt, and then spawn the executor with a visible `Agent` tool call. `bin/card-plan` (the planning worker) is a different case: it rewrites the card itself, which is executor-shaped work, so it stays covered by the original rule and should not be used to hide that step.

**One thing this rule does not cover, settled on 2026-08-20.** When the ordinary `Agent` tool call returns saying the agent "is working in the background", that is only how the tool reports itself back to me — Alex still watches that agent's turns as they happen in his own terminal, and he confirmed it in those words. So a plain `Agent` spawn, with no `isolation` or background flag of my own, satisfies this rule in full, and there is nothing to apologise for or warn him about. Do not raise it as a concern again; the rule is aimed at the things that genuinely hide a run from him — `Workflow`, an explicit background or isolation mode, and a wrapper script that swallows the agent's turns.

This is about *visibility*, a different question from [[feedback_reviewer_agent]], which governs *permission* to spawn at all (only on Alex's explicit word), and from [[feedback-verify-executor-model]], which governs *which model* actually ran the work.
