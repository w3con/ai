---
name: feedback-clone-config-verbatim
description: When a new plan derives one node/service/host's config from an already-proven, already-working one, copy the proven flags/values verbatim — never re-derive them by reasoning about what a flag's name suggests.
metadata:
  type: feedback
---

When a plan calls for standing up a new instance of something that already has a working, live twin — a new validator node cloned from an existing one, a new service cloned from a sibling service, any case where "this should behave identically to that other thing we already run" — the correct move is to copy the proven configuration byte-for-byte for anything that is not required to differ, and change only the fields that genuinely must differ per instance (name, ports, volumes, the address that makes this instance reachable). Do not re-derive individual settings by reasoning about what they sound like they should be.

**Why:** on Pilier's validator-C-onboarding plan (2026-07-20), the phase that wrote `docker-compose.validator-c.yml` needed an RPC-exposure flag identical in effect to the one already running successfully on the live `gra9` nodes. Instead of copying that already-proven line, it reasoned from the flag's name: `--unsafe-rpc-external` sounds more dangerous than `--rpc-external`, so it chose the plainer-sounding one as the "safer" pick. That reasoning was backwards — the two flags are functionally identical (the binary's own `--help` says so verbatim: "`--unsafe-rpc-external` … Same as `--rpc-external`"), the real safety comes from a separate `--rpc-methods=safe` flag that was already correctly present either way, and the CLI's own validator-safety gate outright refuses the plainer-named flag when `--validator` is also set — so the "safer-sounding" choice wasn't even a working alternative, just a broken one. The mistake only surfaced live, at first boot of the real validator, well after the plan and the artifact had both been written and reviewed.

**How to apply:** when a new plan phase's brief is "write a config for a new X that should behave like our existing X," instruct verbatim reuse explicitly — point at the exact proven file/line to copy from, rather than describing the desired end-state in prose and leaving the writer (agent or self) to reconstruct it from first principles. Reasoning about what a setting "should" be, from its name or from general documentation, is exactly the failure mode: it substitutes plausible-sounding judgment for a config that is already known to work. This is the infra-config sibling of [[design-reproduce-not-improvise]] (Validité, pixels instead of flags) — same underlying rule, reproduce the proven artifact exactly, don't improvise a lookalike from reasoning about it — applied wherever a plan clones one already-working thing into a new instance.
